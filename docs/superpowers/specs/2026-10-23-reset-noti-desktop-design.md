# 리셋권 알림 데스크톱 앱 — 설계

작성일: 2026-10-23

## 1. 목적

Claude(Anthropic)와 Codex(OpenAI)는 사용량 한도를 즉시 초기화해 주는 **리셋권**을 가끔 지급한다. 리셋권은 만료 시각이 있고, 안 쓰면 사라진다. 사용자는 Claude/Codex 계정을 **여러 개** 쓰고, 계정마다 리셋권이 따로 생긴다. 각 계정의 리셋권이 새로 생겼을 때, 그리고 만료가 다가올 때 Windows 알림으로 알려주는 앱이 필요하다.

같은 회사 동료 등 다른 사람도 **각자 자기 PC에 설치해서** 쓴다. 로그인 토큰은 각자의 PC 밖으로 나가지 않는다.

이 문서는 이미 동작하는 Python 프로토타입(`reset_noti.py`, 단일 계정, 작업 스케줄러 실행)을 **여러 계정을 관리하는 Windows 앱**으로 바꾸는 설계다. 프로토타입에서 검증한 API 응답과 알림 규칙은 그대로 가져간다.

## 2. 목표 / 비목표 / 안티목표

**목표**
- 앱 안에서 Claude 계정과 Codex 계정을 각각 여러 개 추가, 재인증, 제거한다. 추가하면 브라우저에서 OAuth 로그인이 진행된다.
- 계정마다 리셋권 개수와 가장 빠른 만료 시각을 보여준다.
- 새 리셋권이 생기면 알린다. 만료 72시간 전과 24시간 전에 알린다. 정확한 만료 시각을 기준으로 한다.
- 다른 사람에게 설치 파일 하나로 줄 수 있다.

**비목표**
- "시스템 기본값" 계정, 즉 이 PC의 Claude Code나 Codex에 원래 로그인된 계정을 자동으로 쓰는 기능은 넣지 않는다. 사용자가 명시적으로 뺐다. 그 계정도 앱에서 다시 추가하면 된다.
- 사용량 %나 5시간/주간 한도는 표시하지 않는다.
- 여러 사람의 정보를 서버에 모으지 않는다.

**안티목표** (동작하더라도 실패로 본다)
- 리셋권을 **사용(consume)하는** 요청을 보내면 안 된다. 앱은 조회만 한다.
- 토큰이 로그, 화면, 알림에 노출되면 안 된다.
- 앱이 사용자의 기존 `~/.claude`나 `~/.codex` 로그인 상태를 바꾸거나 망가뜨리면 안 된다.
- 같은 알림이 반복해서 뜨면 안 된다.

## 3. 사용자가 정한 것

- **앱 형태**: Windows 앱이다. 설정 화면은 사용자가 보여준 Orca의 "AI 제공자 계정" 화면처럼 생겼다. Claude 섹션과 Codex 섹션이 따로 있고, 섹션마다 [+ 계정 추가] 버튼과 계정 목록이 있다.
- **계정 한 줄**: `이메일 · 리셋권 N개 · 10/30(금) 04:13 만료  [재인증] [제거]` 형식이다. 시각은 한국 시간(KST)이다. 리셋권이 없으면 `리셋권 없음`으로 표시한다.
- **알림 시점**: 새 리셋권이 생겼을 때, 만료 **72시간 전**, **24시간 전**. 새벽이어도 정확한 시각 기준으로 알린다(사용자가 확인한 사항).
- **알림 모양**: "B 스타일"이다. 제목, 본문 1~2줄, 서비스 로고(Claude는 주황 방사형 별, Codex는 초록 `>_`), 버튼 [사용량 페이지 열기] [닫기]로 구성한다. 문구 예시:
  - `Codex(회사) 리셋권이 생겼어요` / `Full reset · 11/7(토) 08:41까지` / `현재 2개 보유`
  - `Codex(회사) 리셋권 72시간 남음` / `10/30(금) 04:13 만료`
  - `Claude(개인) 리셋권 24시간 남음` / `10/30(금) 04:13 만료 · 안 쓰면 사라져요`
  - 괄호 안의 계정 이름은 사용자가 계정을 추가할 때 붙인 별칭이다. 별칭이 없으면 이메일을 쓴다.
- **배포**: 각자 자기 PC에 설치한다.
- **자동 업데이트**: 데이터 출처가 비공식이라 수정판을 빨리 배포해야 한다. 그래서 Tauri updater 플러그인으로 앱이 시작할 때와 하루에 한 번 새 버전을 확인하고, 사용자 확인 후 설치한다. 이를 위해 다음이 필요하다.
  - 업데이트 서명 키 한 쌍. 비밀 키는 저장소에 넣지 않는다.
  - 배포 위치. 내 판단으로 **GitHub Releases**와 `latest.json`으로 정했다. updater가 인증 없이 받아야 하므로 릴리스에 접근할 수 있어야 한다. 저장소 공개 여부는 저장소를 만들 때 사용자가 정한다.
  - 태그를 푸시하면 빌드, 서명, 릴리스 업로드를 하는 GitHub Actions 워크플로.

## 4. 기술 결정 (내 판단, 사용자에게 알렸고 이의 없음)

- **Tauri 2**를 쓴다. 백엔드는 Rust, 화면은 웹(HTML/TS)이다. 이 PC에 Rust 1.96, Node 22, pnpm이 있다. 결과물이 작은 설치 파일(NSIS 또는 MSI)이라 배포하기 쉽고, 트레이와 알림을 지원한다.
- **트레이 상주**: 창을 닫아도 트레이에 남는다. Windows 로그온 시 자동 시작하고, 이 설정은 기본으로 켜고 설정에서 끌 수 있다. 1시간마다 모든 계정을 확인한다. 화면에 [지금 확인] 버튼을 둔다.
- **로그인**: 앱은 OAuth를 직접 구현하지 않는다. 계정마다 앱 데이터 폴더 아래에 전용 디렉터리를 만든다. 그다음 **공식 CLI 로그인을 그 디렉터리를 지정해서 실행**한다. 사용자 입장에서는 버튼을 누르면 브라우저 OAuth 화면이 뜬다. 공식 클라이언트를 흉내 내는 방식(Claude Code나 Codex의 client_id로 직접 PKCE 흐름을 구현)은 약관 위험 때문에 쓰지 않는다.
  - Claude: 환경변수 `CLAUDE_CONFIG_DIR=<계정 디렉터리>`를 지정해 `claude auth login`을 실행한다.
  - Codex: 환경변수 `CODEX_HOME=<계정 디렉터리>`를 지정해 `codex login`을 실행한다.
  - 따라서 **사용하는 PC에 `claude`와 `codex` CLI가 설치돼 있어야** 한다. 쓰는 서비스의 CLI만 있으면 된다. CLI가 없으면 해당 섹션의 [계정 추가] 버튼 자리에 "Claude Code CLI가 필요합니다" 안내를 띄운다.
- **기존 Python 프로토타입**: 앱을 설치한 뒤 사용자가 작업 스케줄러의 `ResetNoti` 작업을 제거한다(`uninstall.ps1`). 앱이 이 작업을 자동으로 지우지는 않는다. README에 안내한다.

## 5. 데이터 출처 (프로토타입에서 실제로 확인함)

### Codex: 공식 app-server (권장, 검증 완료)
- `CODEX_HOME=<계정 디렉터리> codex app-server`를 띄우고 stdio로 JSON-RPC를 주고받는다. 순서는 `initialize`, `initialized` 알림, `account/rateLimits/read` 요청이다.
- 응답의 `rateLimitResetCredits.credits[]`에는 `id`, `resetType`, `status`, `grantedAt`(unix 초), `expiresAt`(unix 초), `title`, `description`이 들어 있다. `status == "available"`인 것만 센다.
- 토큰 갱신은 Codex가 직접 한다. 앱이 토큰 파일을 읽을 필요가 없다.
- 이메일 같은 계정 정보는 `account/read`에서 가져온다. 이 PC에서 `result.account`의 키가 비어 있었으므로 **빌더가 실제 응답 형태를 확인해야** 한다. 프로토콜 스키마는 `codex app-server generate-json-schema --out <dir>`로 만들 수 있다. 실패하면 `<계정 디렉터리>/auth.json`의 id_token(JWT) 안 `email` 클레임을 쓴다.
- 대안 경로: `GET https://chatgpt.com/backend-api/wham/rate-limit-reset-credits`에 헤더 `Authorization: Bearer`와 `ChatGPT-Account-ID`를 붙여 호출한다. 비공식이고 토큰 갱신을 직접 해야 하므로 쓰지 않는다.

### Claude: 비공식 내부 API
- `GET https://api.anthropic.com/api/oauth/usage?cedar_ember=1&skip_spend=1`에 헤더 `Authorization: Bearer <accessToken>`와 `anthropic-beta: oauth-2025-04-20`을 붙인다. 토큰은 `<계정 디렉터리>/.credentials.json`의 `claudeAiOauth.accessToken`이다(프로토타입과 같은 구조라고 가정, 빌더가 확인).
- 리셋권 정보는 `cedar_ember` 객체에 있다. 확인된 키는 `eligible`, `ineligible_reason`, `at_limit`, `exhausted`, `grants`, `next_grant_id`, `weekly_resets_at`, `cooldown_until`, `event_props`다. **리셋권이 있는 계정으로는 확인하지 못해서 `grants[]` 원소의 형태를 모른다.** Claude Code 바이너리 문자열에는 `grant_id`, `resets_left`, `resets_left_total`, `full reset`, `weekly reset`이 보인다. 프로토타입의 `parse_claude`처럼 관대하게 읽는다. id는 `grant_id`나 `id`, 종류는 `kind`, `reset_type`, `type` 중 있는 것, 만료 시각은 `expires_at`, `expiresAt`, `expires`, `valid_until` 중 있는 것을 쓴다. 문자열 원소도 허용한다.
- 처음 보는 `grants` 형태를 만나면 **원문을 로그에 남긴다**(토큰 제외).
- 이메일은 `claude auth status --json`을 `CLAUDE_CONFIG_DIR`를 지정해 실행하면 나오는 `email`과 `orgName`에서 가져온다(검증 완료).
- **토큰 갱신(미검증, 가장 큰 위험)**: access token은 만료된다. 앱은 `.credentials.json`의 `expiresAt`(ms)을 확인해서 만료가 임박했거나 지났으면 같은 환경변수로 `claude auth status --json`을 실행한 뒤 파일을 다시 읽는다. 이 명령이 토큰을 갱신하는지는 **확인하지 못했다**. 구현의 첫 단계에서 검증한다(7절).
  - **`auth status`로 갱신되지 않을 때 (사용자 결정: B)**: 토큰이 만료됐거나 10분 안에 만료되면, 같은 환경변수를 지정해 아주 짧은 `claude` 비대화형 명령을 실행해서 공식 CLI가 토큰을 갱신하게 한다(예: `claude -p "ok" --model haiku --max-turns 1`). 이때 계정 사용량이 조금 줄어드는 것은 사용자가 감수하기로 했다. 갱신이 필요할 때만 실행하고, 매 확인마다 실행하지 않는다. 가장 싸게 갱신하는 명령과 옵션은 스파이크에서 정한다.
  - 앱이 Claude Code의 client_id로 직접 토큰을 갱신하는 방법은 **쓰지 않는다**(약관 위험).
  - 위 방법이 모두 실패하면 계정 줄에 `재인증 필요`를 표시하고, 알림은 계정마다 하루에 한 번만 보낸다.

### 공통
- 두 API 모두 공식 공개 API가 아니어서 CLI가 업데이트되면 깨질 수 있다. 응답을 읽지 못하면 계정 줄에 `확인 실패`를 표시하고 로그를 남긴다. 앱은 죽지 않는다.

## 6. 알림 규칙 (프로토타입 `plan()` 그대로, 테스트로 검증됨)

상태는 계정별로 따로 둔다(`seen`: 본 리셋권 id, `sent`: 보낸 알림 키 `<grantId>:<72|24>`).

1. 계정을 처음 확인할 때: 리셋권이 있으면 요약 알림을 한 번 보낸다(`Codex(회사) 리셋권 2개 보유 중` / `가장 빠른 만료: …`). 이때 있는 리셋권은 모두 `seen`으로 기록한다. 리셋권이 없으면 알리지 않는다.
2. 그 뒤 처음 보는 id가 나타나면 `리셋권이 생겼어요` 알림을 보낸다.
3. 만료 알림: 남은 시간이 72시간 이하이면 72시간 알림, 24시간 이하이면 24시간 알림을 보낸다. 해당하는 것 중 **가장 임박한 것 하나만** 보내고, 해당하는 키는 모두 `sent`에 넣는다. 그래서 72시간 시점을 놓쳤다면 24시간 알림만 간다.
4. 새로 생긴 리셋권이 이미 72시간이나 24시간 안에 있으면 "생겼어요" 알림 하나로 대신하고, 만료 알림 키는 `sent`로 처리한다.
5. 만료 시각이 없는 리셋권에는 만료 알림을 보내지 않는다. 이미 만료된 리셋권은 무시한다.
6. 같은 계정을 두 번 추가하지 못하게 막는다. 추가가 끝났을 때 이메일과 조직(Claude) 또는 계정 id(Codex)가 이미 있는 계정과 같으면 "이미 추가된 계정" 안내를 띄우고 새 디렉터리를 지운다.

### 검토 후 추가한 결정 (내 판단)

7. **정확한 시각에 알림**: 확인할 때마다, 그리고 절전에서 깨어날 때마다 리셋권별로 T-72h와 T-24h 타이머를 다시 잡는다. 그래서 1시간 주기와 상관없이 정확한 시각에 알림이 간다. 깨어났을 때 이미 지난 시점이면 규칙 3에 따라 가장 임박한 알림 하나만 즉시 보낸다.
8. **확인 실패 중에도 만료 알림**: 만료 알림은 마지막으로 성공한 조회에서 저장한 리셋권(계정별 `grants` 캐시)을 기준으로 보낸다. 마지막 성공 조회가 2시간보다 오래됐으면 본문 끝에 `(마지막 확인: 10/28 15:00)`을 붙인다. 이미 사용한 리셋권에 대한 알림이 잘못 갈 수도 있지만, 24시간 알림을 놓치는 것보다 낫다고 판단했다. 캐시는 `state.json`에 계정별로 둔다.
9. **Claude 리셋권 개수**: 원소에 `resets_left`가 있으면 그 값의 합을 쓰고, 없으면 원소 수를 쓴다. "새 리셋권" 판단은 id가 새로 생겼거나 같은 id의 `resets_left`가 늘었을 때로 한다. 실제 형태는 리셋권이 있는 응답을 확인한 뒤 고친다(원문 로그 기반 후속 수정).

알림 클릭이나 [사용량 페이지 열기] 버튼은 다음 주소를 연다.
- Claude: `https://claude.ai/settings/usage`
- Codex: `https://chatgpt.com/codex/settings/usage` (미확인. 빌더가 확인하고, 틀리면 `https://chatgpt.com/`의 사용량 설정 경로로 바꾼다.)

알림 앱 이름은 "리셋권 알림"이다.

## 7. 구현 순서 제안 (위험한 것부터)

1. **Claude 토큰 갱신 검증 스파이크**: 별도의 `CLAUDE_CONFIG_DIR`로 로그인한다. `.credentials.json`의 `expiresAt`이 지난 뒤(또는 사본의 값을 과거로 바꾼 뒤) `claude auth status --json`을 실행하고, `accessToken`과 `expiresAt`이 갱신되는지 본다. 결과에 따라 갱신 전략을 확정하고 이 문서에 기록한다. 갱신되지 않으면 "재인증 필요" 흐름이 주 경로가 된다.
2. **CLI 로그인을 GUI에서 띄울 수 있는지 검증**: `claude auth login`과 `codex login`이 콘솔 없이 실행될 때 브라우저를 열고 정상 종료하는지 확인한다. 터미널 입력(코드 붙여넣기 등)을 요구하면, 앱이 숨긴 콘솔 대신 보이는 콘솔 창으로 실행하는 대안을 쓴다.
3. Codex app-server 클라이언트(Rust)를 만든다.
4. 알림 규칙을 Rust로 옮긴다. 프로토타입 `test_reset_noti.py`의 테스트 케이스를 그대로 옮긴다.
5. 화면, 트레이, 자동 시작, 설치 파일 순서로 만든다.

## 8. 저장 위치

- 앱 데이터: `%APPDATA%\ResetNoti\`
  - `accounts\claude-<uuid>\`, `accounts\codex-<uuid>\`: 계정별 CLI 설정 디렉터리
  - `accounts.json`: 계정 목록(서비스, uuid, 별칭, 이메일, 추가 일시)
  - `state.json`: 알림 상태
  - `reset_noti.log`
- [제거]는 확인창을 띄운 뒤 계정 디렉터리를 지운다. 서버 쪽 로그아웃은 하지 않는다.

## 9. 빌더에게 맡기는 것

- 화면 세부 디자인. Orca 스크린샷처럼 어두운 테마, 섹션 카드 구성이 기준이다.
